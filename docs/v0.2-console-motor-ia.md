# v0.2: Console Be Safe, motor de cenários e IA local

Desenho da segunda versão. A v0.1 entrega a VM, as ferramentas e o treinamento. A v0.2 transforma a VM num **plantão simulado**: alertas chegam ao Wazuh ao longo do tempo, o aluno trabalha a fila, abre tickets no Console e recebe nota. A IA local faz o papel do N2 e das pessoas envolvidas.

## Visão geral

```
                         semente da VM (gerada no primeiro boot)
                                       │
 cenarios/*.yml ──▶  MOTOR  ──────────┼──▶ /var/log/besafe/eventos.json ──▶ WAZUH ──▶ alertas na fila
 (linha do tempo,    (sorteia hosts,   │        (JSON, um evento por linha)     (regras 100100+)
  verdade, dicas)     usuários, IPs,   │
                      horários)        └──▶ banco do Console (SQLite): plantão, verdade, serviços simulados
                                                      │
                                                      ▼
                                   CONSOLE BE SAFE (http://localhost:8080)
                     plantão · tickets · nota · Intel · diretório · inventário · caixa de phishing
                                                      │
                                                      ▼
                                   IA LOCAL (llama.cpp, modelo pequeno, sob demanda)
                               mentor N2 · usuária simulada · copiloto do SOC (lab de injeção)
```

## Decisões

| Tema | Decisão | Motivo |
|---|---|---|
| Linguagem | Python 3.12 (o do Ubuntu 24.04) | já está na VM; bibliotecas instaladas num venv no build |
| Console | FastAPI + SQLite + HTML/JS puro (sem etapa de build de front) | leve, offline, fácil de manter |
| Serviços | `besafe-console.service` (usuário de sistema `besafe`), só em `127.0.0.1:8080` | mesmo princípio do Wazuh: nada exposto |
| Injeção no SIEM | arquivo JSON lido pelo Wazuh (`localfile` com `log_format json`) + regras próprias (IDs 100100 em diante) | sem agente, sem Windows; o aluno vê os alertas na fila real do Wazuh |
| Semente | 64 bits aleatórios no primeiro boot, legível só pelo serviço | cada cópia gera cenários diferentes: resposta de um aluno não vale para outro |
| Nota | determinística, comparando o ticket com a "verdade" do cenário | a IA nunca dá nota |
| IA | `llama-server` (llama.cpp, MIT) com modelo GGUF quantizado em Q4 | binário pequeno, API compatível com OpenAI, roda em CPU |
| Modelo | candidatos com licença que permite redistribuir: **Qwen3-4B** (Apache 2.0) e **Phi-4-mini** (MIT); escolha por teste em PT-BR | modelos com licença restritiva ficam de fora |
| Carga da IA | o Console sobe o `llama-server` quando o aluno abre um chat e derruba após 10 minutos parado | economiza cerca de 3 GB de RAM fora de uso |

## Motor de cenários

Um cenário é um arquivo YAML com:

- **atores**: papéis (vítima, máquina, atacante) que o motor preenche a partir da semente (usuários do diretório, máquinas do inventário, IPs de documentação para o lado de fora);
- **linha do tempo**: eventos com atraso relativo (`+0s`, `+40s`...) e campos;
- **verdade**: classificação esperada (verdadeiro positivo, falso positivo, verdadeiro positivo benigno), severidade, se deve escalar, indicadores e táticas do ATT&CK;
- **dicas**: três níveis, do mais vago ao mais direto, usados pelo mentor.

Um **plantão** sorteia um conjunto de cenários (com mais ruído que ataque, como na vida real) e espalha os eventos ao longo do tempo escolhido (padrão: 60 minutos).

Os eventos são **metadados**, no formato que um SIEM recebe (processo, linha de comando, IPs, Event ID, usuário). Não há código malicioso, nem exploração, nem tráfego real: só registros.

## Console

| Tela | Conteúdo |
|---|---|
| Plantão | iniciar/encerrar, progresso, alertas pendentes |
| Tickets | um ticket por caso: classificação, severidade, escalar, indicadores, linha do tempo, texto |
| Nota | por ticket e por plantão: classificação, severidade, escalonamento, indicadores, tempo de triagem e dicas usadas |
| Intel | reputação de IP, domínio e hash (resultados coerentes com a semente, às vezes ambíguos) |
| Diretório | colaboradores: cargo, setor, gestor, horário, férias |
| Inventário | máquinas: função, setor, criticidade, dono |
| Caixa de phishing | e-mails reportados pelos colaboradores (do cenário) |
| Mentor | chat com o N2; cada nível de dica custa pontos |

## IA local

- **Mentor N2**: recebe só a **dica do nível atual** e a pergunta do aluno. Ele nunca vê a verdade do cenário, então não tem como entregar a resposta.
- **Pessoas simuladas**: a colaboradora que reportou o phishing responde perguntas a partir de uma ficha do cenário (o que ela lembra, o que ela fez).
- **Copiloto do SOC (lab de injeção)**: resume alertas para o analista. Num cenário, o atacante coloca um texto num campo do evento tentando convencer o copiloto de que está tudo bem. O aluno precisa perceber a contradição entre o resumo e o evento bruto.
- Temperatura baixa e respostas curtas; sem a IA (máquina fraca), o Console mostra as dicas escritas.
